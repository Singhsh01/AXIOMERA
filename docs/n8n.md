# n8n in Axiomera

## Why n8n is central

n8n executes every multi-step process in the product: intake (A), incident handling and SLA monitoring (B), tender processing (C), deadline monitoring (D), human approvals with durable waits (E) and dead-lettering (Z). The API is never asked to sleep, poll or retry on its own; that is n8n's job ([ADR 0002](adr/0002-n8n-orchestrates-api-owns-state.md)).

Verified in development against n8n **1.123** (npm `n8n@1.123.92`): signed intake → case → approvals waiting in Wait nodes → decision in the web app → resume → authorise → execute → verify; retries on injected Jira failures (attempts 1–2 failed, 3 succeeded); retries exhausted → error workflow → dead letter → replay; Wait-node executions surviving an n8n restart and resuming afterwards.

## Source of truth for workflow definitions

`n8n/workflows/*.json` are what n8n imports. They are generated by `n8n/build_workflows.py`, which guarantees for every HTTP node:

- `X-Orkestr-Service-Token` from `$env`, `X-N8N-Execution-Id: {{$execution.id}}`, `X-Orkestr-Workflow`, `X-Orkestr-Node` (equal to the node name — used for step correlation) and `X-Correlation-Id`;
- `retryOnFail` with 3–5 tries and 2–5 s waits; explicit timeouts;
- `settings.errorWorkflow = OrkZ0ErrorHandler` on every workflow except Z;
- a content-addressed `versionId` (n8n resolves the active version by this id; a constant id meant re-imports silently kept running the old version — found and fixed during development).

Workflow IDs are fixed (`OrkA0CustomerIntk`, …) so the error workflow reference and the sub-workflow call from A to E survive re-imports. CI regenerates the JSON and fails on drift. After editing a workflow in the n8n editor, export it and port the change into the generator.

## Bootstrap

The `n8n-init` container runs `n8n/bootstrap.sh` once: imports all workflows, activates A–E by id and leaves Z inactive (error workflows run without activation). `make n8n-import` repeats this against a running stack.

Required environment (see `x-n8n-env` in `docker-compose.yml`):

| Variable | Why |
|---|---|
| `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` | workflows read `ORKESTR_API_URL`, `ORKESTR_SERVICE_TOKEN`, `ORKESTR_WEBHOOK_SECRET` via `$env` |
| `NODE_FUNCTION_ALLOW_BUILTIN=crypto` | HMAC verification in Code nodes |
| `WEBHOOK_URL` | base of `$execution.resumeUrl`; the API rewrites the host to its internal n8n URL when resuming |
| `N8N_ENCRYPTION_KEY` | set your own; protects n8n credentials at rest |

## Security

- **Inbound webhooks** (A, B, C, D, E) use `rawBody` and verify `HMAC-SHA256(secret, timestamp + "." + body)` with a 5-minute window and `crypto.timingSafeEqual` before anything else runs. Invalid requests get 401 (A, B, C) or stop the execution (D, E).
- **Resume callbacks** to Wait nodes are signed over `timestamp.approval_id.decision`, and the next node re-checks authorisation against the database (decider active, role rank, expiry, scope hash) — a forged resume cannot execute anything.
- **n8n → API** uses a shared service token. The service principal has a fixed permission set and can never decide approvals.
- **Exposure.** Compose binds n8n to `127.0.0.1` only. In production put the editor behind SSO/VPN, set `N8N_SECURE_COOKIE=true` behind TLS, and expose only `/webhook/*` and `/webhook-waiting/*` publicly if external systems must reach them.

## Email attachments

Workflow C is triggered by the API when a document is uploaded. To accept tenders by email, add an IMAP/Gmail trigger in n8n that posts the attachment to `POST /api/v1/rfps` with the service token; the rest of the pipeline is unchanged. This is not shipped as an active workflow because it needs mailbox credentials.
